# PlayGround Project (V2: Multi-Module Hexagonal Architecture)

## 프로젝트 소개

`PlayGround`는 아키텍처의 점진적인 진화 과정을 기록하기 위한 토이 프로젝트입니다.  
V2는 **헥사고날 아키텍처를 멀티 모듈 구조로 확장**한 단계로,  
도메인 간 경계를 코드 레벨에서 강제하는 것을 목표로 합니다.

이 단계의 핵심은 새로운 아키텍처 스타일을 도입하는 것이 아니라,  
**도메인이 증가함에 따라 흐려지기 쉬운 경계를 구조적으로 통제**하는 데 있습니다.

---

## Why V2 Exists

V1.5에서는 헥사고날 아키텍처를 적용하여  
도메인 중심의 구조와 의존성 역전 원칙을 확립했습니다.

그러나 도메인이 점차 추가되면서,  
단일 모듈 내 패키지 경계만으로는 다음과 같은 한계가 드러났습니다.

- 도메인 간 협력이 늘어날수록 내부 구현에 대한 의존이 발생
- 관례에 의존한 경계로 인해, 시간이 지날수록 결합도가 증가
- 구조적으로 잘못된 의존이 컴파일 단계에서는 드러나지 않음

V2는 이러한 문제를 해결하기 위해  
각 도메인을 독립적인 모듈로 분리하고,  
의존성 방향을 **컴파일 타임에 강제**하는 멀티 모듈 구조로 전환합니다.

---

## V2 Architecture Overview

V2에서는 각 도메인을 독립적인 Gradle 모듈로 구성합니다.

- order
- product
- user
- payment
- …

각 도메인 모듈은 V1.5에서 정립한 헥사고날 아키텍처 구조를 그대로 유지합니다.

- domain
- application (port / service)
- adapter (persistence / presentation)

멀티 모듈 전환의 목적은  
아키텍처 스타일 변경이 아니라 **경계의 고정**입니다.

---

## Contract Module 도입 배경

도메인이 분리되더라도,  
실제 비즈니스 흐름에서는 도메인 간 협력이 불가피합니다.

예를 들어 주문 도메인은  
상품과 사용자 도메인의 정보에 의존하며,  
이 과정에서 양방향 협력이 자연스럽게 발생합니다.

그러나 멀티 모듈 구조에서는  
도메인 간 양방향 의존 관계를 허용할 수 없습니다.

- 순환 참조 발생
- 모듈 경계 붕괴
- 의존성 그래프의 복잡도 증가

이를 해결하기 위해 V2에서는  
도메인 간 협력을 위한 **contract 모듈**을 도입합니다.

---

## Contract Module의 역할

contract 모듈은 도메인 간 통신을 가능하게 하지만,  
그 책임은 명확히 제한됩니다.

- 외부 도메인에 제공되는 최소한의 인터페이스 정의
- DTO / Command / Query 모델 제공
- 도메인 내부 구현 노출 차단

contract 모듈에는  
**비즈니스 로직을 포함하지 않습니다.**

비즈니스 규칙은 항상  
각 도메인의 application/service 계층에 위치하며,  
contract는 오직 협력을 위한 경계 역할만 수행합니다.

이를 통해 다음을 달성합니다.

- 도메인 간 의존성 방향의 단방향 유지
- 순환 참조의 컴파일 타임 차단
- 도메인 경계의 명확한 가시화

---

## Trade-offs

멀티 모듈 구조와 contract 모듈 도입은  
다음과 같은 비용을 동반합니다.

- 초기 설계 및 설정 비용 증가
- 단순한 기능 변경에도 수정 범위 확대
- 개발 속도 저하

V2는 이러한 비용을 감수하더라도,  
도메인 경계가 흐려지는 시점을 늦추고  
장기적인 유지보수성을 확보하는 선택을 했습니다.

---

## How This Leads to V2.5

V2는 구조적으로 안정된 모놀리스를 만드는 단계입니다.

그러나 실제 운영 환경에서는  
구조보다 성능, 동시성, 관측성이 더 큰 문제가 됩니다.

V2.5에서는 이 구조 위에서  
의도적으로 병목을 만들고,  
측정과 개선을 통해 운영 관점의 문제를 다룹니다.
