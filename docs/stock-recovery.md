# 재고 예약 복구 정책

## 자동 복구 범위

Redis는 주문별 예약 수량과 처리 상태를 저장한다. 복구 작업은 기존 주문 테이블을 조회하며, 별도 JPA Entity나 테이블을 추가하지 않는다.

| DB 조회 결과 | Redis 처리 |
| --- | --- |
| `COMPLETED` | 예약 재고 확정 재시도 |
| `FAILED`, `CANCELLED` | 예약 재고 해제 재시도 |
| `PENDING` | 예약 유지 |
| 주문이 조회되지 않음 | `UNKNOWN`으로 처리하고 예약 유지 |
| DB 조회 실패 | 예약 유지 후 재시도 |

DB에 주문이 보이지 않아도 주문 생성 트랜잭션이 진행 중일 수 있다. 따라서 경과 시간만으로 롤백을 추정하거나 예약을 해제하지 않는다. 이미 확정된 주문의 취소·환불에 따른 재고 반환은 이 복구 작업의 범위가 아니다.

## 재시도와 재시작

- 주문 예약 Lua 실행에서 복구 대상 ZSet에 주문 ID를 함께 등록한다.
- 10초 간격으로 최대 100건을 조회하고, 각 주문의 다음 시도 시각을 30초 뒤로 미룬다.
- 확정·해제에 성공하면 복구 대상에서 제거한다. 중복 실행은 주문별 상태로 차단한다.
- 앱 시작 시 `SCAN`으로 남은 예약 Hash를 찾아 복구 인덱스를 재구성한다.
- 재고 초기화는 `SETNX`를 사용해 기존 기준 재고와 예약·확정 수량을 덮어쓰지 않는다.

## DB 재고 동기화

변경 상품 표시(dirty Set)는 DB 저장에 성공한 뒤 제거한다. 그 사이 확정 수량이 달라졌다면 표시를 유지하여 다음 배치에서 다시 저장한다.

현재 동기화 모델은 판매 확정에 따른 재고 감소만 지원한다. 이전 배치가 늦게 저장되어 DB 재고를 늘리지 않도록 조건부 UPDATE를 사용한다. 입고·반품 등 재고 증가 기능을 추가할 때는 버전 관리와 기준 재고 갱신 정책을 별도로 설계해야 한다.

## 남은 한계와 확인 대상

- 주문 생성 롤백 후 Redis 보상도 실패하면 DB에 없는 예약이 남을 수 있다. 이 예약은 자동 정리하지 않으며, 트랜잭션 종료와 결제 여부를 확인한 뒤 별도 보상해야 한다. `UNKNOWN` 예약은 계속 재조회한다.
- 예약 Hash와 재고 키가 보존된 앱 재시작을 대상으로 한다. Redis 전체 데이터 유실이나 일부 키 유실을 자동으로 복원하지는 않는다. 데이터 유실 시 쓰기를 중단하고 DB·결제 기록과 백업을 대조해야 한다.
- 지연된 중복 요청을 차단하기 위해 확정·해제 기록에는 TTL을 두지 않았다. 기록 보관과 안전한 정리 정책은 후속 과제다.
- 테스트는 기존 H2와 jedis-mock 환경을 사용한다. 실제 Redis 장애·영속성 및 운영 DB 검증을 대신하지 않는다.

## 검증

JDK 21에서 다음 명령을 실행한다.

```shell
./gradlew -p monolith :module-order:test :module-product:test :module-app:compileKotlin
```

주문 상태별 복구, 미커밋 주문 보존, 조회 실패 후 재시도, 복구 인덱스 재구성, 초기화 시 기존 재고 보존, DB 저장 실패 및 동기화 중 추가 확정을 검증한다.
